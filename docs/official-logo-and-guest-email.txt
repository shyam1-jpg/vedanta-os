SAFE REMEDIATION INCLUDED
- Public, no-store guest auth-options endpoint returns only whether email-code delivery is configured.
- Registration checks availability before sending; a missing connection shows contact options instead of asking the guest to retry indefinitely.
- New guests request verification before account creation. Existing access-code sign-in and signed-in enquiries stay available.
- Already-issued codes can still be submitted if delivery later becomes unavailable.
- No guest account is opened without verification; ALLOW_UNVERIFIED_GUEST_BOOTSTRAP remains false.
- Delivery failures log only an allowlisted error category, not SMTP secrets, recipient details or verification codes.

Identify the authorised Vedanta sender mailbox and its provider. Add SMTP_URL and MAIL_FROM securely in the existing vedanta-api Render service's Environment settings. An ordinary Microsoft sign-in configuration alone does not authorise sending mail.
Do not paste mailbox passwords, app passwords or API keys into chat or commit them to GitHub. The provider/administrator must confirm an authenticated sending method is enabled for the chosen sender. Microsoft 365 tenants may require an approved OAuth-capable mail setup rather than password SMTP; do not weaken tenant security to work around this.
No mail provider was purchased, no mailbox was created and no Microsoft permissions were changed by this patch.
After configuration, redeploy once, confirm /guest/auth-options returns email_code:true, and perform one end-to-end code delivery/verification test to an owner-approved mailbox. Configuration presence is not evidence of successful delivery.
